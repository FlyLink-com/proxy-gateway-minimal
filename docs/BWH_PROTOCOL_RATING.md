## What is off

Opening the control-plane process does not create the rating tables. `scripts/protocol-traffic-rating-dry-run.mjs` with exactly `--db` and one absolute path to an existing file opens that file read-only and prints an impact report. Exit 0 means the command ran. The report can still say the schema is absent, partial, checksum-mismatched, or already applied, and it does not write schema, baseline, policy, pending, or ledger rows. `--apply` and `--migrate` exit 2 and do not open a database. No arguments, a relative path, a missing file, or any other target exits 2 and does not fall back to `data/control.sqlite`. No charge is written until an operator records an explicit baseline. A 1× policy without that baseline stays on the legacy raw read.

## Charge

The server stores multiplier units over a fixed denominator of 10000. `0.1` is 1000 units and `10` is 100000 units. `0` and values outside that range are rejected. Admin sends decimal strings. JSON does not carry BigInt.

`N = rawTotalBytes × multiplierUnits + carryIn`. Charged bytes are `floor(N / 10000)` and the remainder stays on the same account, entitlement, request, cycle, and channel. Upload and download are one split of that total. The same raw sample id is charged once. Replay checks the frozen policy and does not move the remainder.

A charged byte count above `Number.MAX_SAFE_INTEGER` is rejected with `rating_overflow` before `Number()` conversion. The value `9007199254740991` at 10× is `90071992547409910`; converting that through `Number` would store `90071992547409904`, so the write is refused instead. `9007199254740991` itself still round-trips.

When a journal batch carries a frozen decision for a raw row that already exists, the sample writer checks that decision in the same transaction. A different decision is `rating_replay_conflict`. A missing charge is `rating_charge_missing`. A version-2 slot of `null` is `rating_decision_required` when that sample is past the baseline boundary. None of those paths inserts a charge, moves the remainder, or advances the journal checkpoint.

A new commit always writes payload version 2 with an explicit rating field. Omitting `freezeRating`, or returning null, stores `rating: null`. After a baseline, the first apply fails with `rating_decision_required` and leaves that pending in place. Recovery of the same pending fails again with `rating_decision_required`. It does not classify the pending as version 1, and it does not insert raw, a charge, or a remainder, or advance the checkpoint. That pending cannot be admitted as a pre-switch leftover.

A version-1 pending is legacy only when a separate `pre-rating-switch` admission matches the digest of that exact payload. Field shape alone does not grant it, and commit never writes the admission. An admitted leftover may insert the raw sample without a charge. If that sample is after the baseline, the rated read still returns `rating_charge_missing`. Samples with no baseline, and samples at or before the baseline boundary, are not backfilled and are not repriced. A missing charge after the boundary is still a read failure; it is not filled with raw bytes or 1×.

An unobserved baseline stays unknown after later samples. It is not stored or displayed as zero. `measured_zero` is the explicit zero. Quota used is the confirmed baseline plus later charges. A missing charge after the boundary fails the read. Raw sample rows are not rewritten.

Changing a multiplier does not rotate credentials, clear a checkpoint, or change the metering binding digest. Once any charge uses a multiplier other than 10000, a raw-only rollback is rejected. Putting multipliers back to 1× affects later samples and keeps the existing charges and remainders.

## Boundary

Admin save writes a pending version. The collector freezes the active policy for the current batch. Recovery replays that frozen decision. The next full interval uses the newly active policy. The first version does not split one sample across the boundary by wall clock. Collection does not admit a version-1 pending and does not call the lifecycle coordinator. An unadmitted leftover stays unapplied.

## Lifecycle

`scripts/lib/protocol-traffic-rating-lifecycle.mjs` is not imported by process startup or by collection. `runProtocolRatingLifecycle` accepts `inspect`, `migrate`, `drain`, `baseline`, or `activate`. Called directly, the requested action records any missing earlier stage under the existing journal writer lock. `runProtocolRatingRollbackCheck` is separate. It records the rollback decision and does not delete charges or restore a database snapshot.

`scripts/protocol-traffic-rating-operator.mjs` is the formal entry over that same lock and those same stage functions. It runs one named action. A missing earlier stage is `rating_lifecycle_prerequisite`; an activate call does not migrate, drain, or record a baseline. The entry rejects extra fields, a relative path, a link, a non-regular file, another database chosen by default, and test hooks such as `persistFault`. Ordinary stdout carries stage names, counts, digests, and an error class. `scripts/protocol-traffic-rating-dry-run.mjs` remains the read-only impact check. Coordinator `inspect` still writes the lock and the stage file. Process start, Admin save, and collection do not call the formal entry. Admin save still writes a pending policy and does not activate it.

After open, the formal entry records the journal directory and, when the database name is an absolute path, the database file. A memory database records the directory only. The identity is the platform device, inode, owner, mode, link count, type, and real path. Size and modification time are not part of it. That snapshot is kept. A later path is not adopted. The entry checks it again on the next turn, once more before it asks for the writer lock, and again inside the original writer lock before the business step. If `writer.lock` is already held, it waits one turn and then either stops with `full_metering_locked` or acquires that same lock and checks again. It does not take a second lock. A mismatch before the step throws `rating_target_unverified` and leaves both the stage file and the rating tables absent. A journal directory replaced while that lock is held does this on the Windows host used here. A second file with the same bytes does not match. Replacing a closed database at the same path does not match. A later write that changes the modification time or size still matches. Replacing `checkpoint.json` with the same bytes keeps the directory identity, and inspect then migrate still return ok. The command output has no path and no identity fields. A relative path, a missing file, and a symlink remain `rating_operator_rejected` and print no path. better-sqlite3 does not expose the descriptor SQLite opened. `db.name`, `PRAGMA database_list`, a path stat, and a descriptor opened again are not accepted as that handle. The probe result on this host is `driver_handle_unexposed`. That is not a Linux file-descriptor proof. The command has no flag for a handle reader. A reader passed beside the whitelisted request can show an opened file whose inode, mode, or owner is not the path; the step then does not start. An extra field on that reader is `rating_operator_rejected`. After migrate has committed, one full operator call sees that kind of drift before the receipt, returns `ok: false` with `rating_target_unverified`, keeps the migration row and the stage file, and does not restore another database over it. On this Windows host, chmod left the reported mode unchanged, the owner stayed unchanged, and replacing the database while it was open returned `EPERM`. Those three are not a live drift proof.

Inspect stores the read-only impact and does not write schema. Migrate refuses a partial schema or a bad checksum before apply. A second apply with the same checksum does not insert another migration row. Drain admits an old version-1 pending only when the caller supplies that payload's digest, then recovers it as raw. The formal entry does not accept an external writer. For a non-empty pending it builds the existing sample writer from the open database, the metering scope, and the stored binding contract, and a version-1 recovery also requires that approved digest. A version-2 pending is recovered with its frozen decisions. A null decision is not admitted as version 1. An invalid or replaced pending stays on disk. After drain is recorded, a newly appeared pending stays on disk and blocks the next stage. Baseline records the supplied resource set, including an explicit empty set. Repeating it does not rebuild rows. Dropping or retargeting an identity is refused. Activate writes an intent for one target version, policy digest, expected active version, and checkpoint before it changes the database. Recovery completes that intent. If the target is already active, it only writes the missing receipt and leaves a later pending policy pending. If the target was replaced or the digest or boundary does not match, it stops with `rating_lifecycle_conflict` and does not activate the replacement. The same checkpoint does not activate another policy after a receipt exists. A moved checkpoint can start a new intent, and the formal entry uses that same rule: the completed receipt stays the only target until the requested checkpoint is the new journal checkpoint and the live active version and pending version and digest match. An unfinished later intent is not replaced by a newer pending policy. A file-backed SQLite run activated that next policy once through the operator after a synthetic commit. The earlier charge stayed on the first policy, the next interval in the same cycle used the new multiplier and the previous remainder, and the baseline row was not rebuilt. A mismatched digest, active version, checkpoint, or an unrecovered journal batch was refused without a new stage write. A parent-directory sync failure before the database change left the first policy active. A receipt failure after the database change was rewritten without activating a newer pending policy. The receipt records `simultaneousProtocolSwitch: false`. Saving a multiplier in Admin remains pending until that activation succeeds.

The intent file is fsynced and renamed over the previous stage record. A failure before rename leaves the previous file and removes the temporary file. A failure of the parent-directory sync happens after rename, so the new file is already visible to this process and is not rolled back. If that visible intent's target is not active yet, the next attempt writes the same intent again before it changes the database. A second parent-directory sync failure leaves the active policy, pending policy, raw rows, charges, remainder, and checkpoint unchanged. If the target is already active, the next attempt only writes that target's receipt and leaves a later pending policy pending. A failed receipt write does not report the stage complete and does not supersede, reactivate, or rewrite the committed policy. A later read of that visible receipt rewrites the same receipt before it reports completion. Another parent-directory sync failure still does not report completion. A later successful sync completes that same receipt. Repeating it does not activate again. Windows cannot fsync a directory, so these hooks prove the process-crash window only. They are not a power-loss proof, and this tree has no Linux directory-fsync run.

A sample older than the rollup cursor is refused. The pending file stays, the checkpoint does not advance, and the remainder stays on its own cycle. A later cycle starts its own remainder at zero.

## Admin

The owned-node card shows VLESS, Hysteria2, and TUIC multipliers only after the schema is installed. Sliders and number fields stay in the browser until a separate confirmation. That confirmation says the change affects later new usage and does not pause or resume supply. The request carries the rating revision and three decimal strings. It uses the Admin session, role, exact Origin, and `no-store`. The legacy console token cannot save it. Invalid input leaves the previous policy in place.
