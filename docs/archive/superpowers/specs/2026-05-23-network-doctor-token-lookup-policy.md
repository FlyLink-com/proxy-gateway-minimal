# Network Doctor Token Lookup Policy

## Goal

Decide whether `scripts/network-doctor.ps1` should read `CONSOLE_TOKEN` from
`.env`, or keep the current narrower token lookup behavior.

This decision is intentionally docs-only. It should prevent future confusion
between runtime `.env` configuration and the Windows diagnostic script's local
operator token lookup boundary.

## Current Token Lookup Behavior

`scripts/network-doctor.ps1` currently looks for the console token in two
places:

1. Process environment: `CONSOLE_TOKEN`
2. Local token store: `.proxy-gateway/console-token`

It does not read:

- project `.env`
- production `.env`
- AWS secret stores
- shell profile files
- any other secret source

When `repair` starts the proxy stack, it calls `/api/proxy/start` on the local
console API and sends the resolved token as a Bearer token. If no token is
available from the current lookup sources, repair cannot authenticate the
proxy-start call.

## Failure Scenario Under Consideration

The scenario being evaluated is:

```text
Operator configured a fixed CONSOLE_TOKEN in .env.
The Node runtime loaded that token.
The current PowerShell process does not have CONSOLE_TOKEN set.
.proxy-gateway/console-token is absent or stale.
network-doctor.ps1 repair cannot authenticate /api/proxy/start.
```

This is a plausible local workflow, but it has not yet been established as a
frequent operational failure in this project.

## Option A: Keep Current Lookup Behavior

Keep `network-doctor.ps1` limited to:

1. Process environment `CONSOLE_TOKEN`
2. `.proxy-gateway/console-token`

Under this option, operators who use a fixed `.env` `CONSOLE_TOKEN` must either:

- expose that value to the current PowerShell process as `CONSOLE_TOKEN`, or
- rely on the local `.proxy-gateway/console-token` generated by the runtime.

Required implementation after this decision:

- Documentation-only clarification in user/operator docs.
- No PowerShell `.env` parser.
- No token source precedence change.
- No runtime change.

## Option B: Add `.env` Fallback

Teach `network-doctor.ps1` to read `.env` when process environment and token
store lookup fail.

This would require deciding and testing:

- precedence between process environment, token store, and `.env`;
- how to parse comments, blank lines, quoted values, escaped characters, and
  whitespace;
- whether malformed `.env` should stop repair or be ignored;
- how to report token-source failures without printing token values;
- how to avoid accidentally reading production `.env` from the wrong path;
- how tests create temporary `.env` files without leaking secrets;
- whether `scripts/proxy.ps1` should share any parser code or remain separate.

## Security And Complexity Comparison

Option A is simpler and keeps `network-doctor.ps1` as a local diagnostic tool,
not a general secret resolver. It has fewer parsing rules, fewer precedence
cases, and a smaller risk of reading the wrong secret source.

Option B may improve convenience for operators who only configure
`CONSOLE_TOKEN` in `.env`, but it increases the script's responsibility. It also
creates a stronger need for targeted PowerShell tests and careful error
messages that never expose token values.

## Recommendation

Use **Option A+** for now:

```text
Keep current token lookup behavior, and document the boundary clearly.
```

Short-term policy:

```text
network-doctor.ps1 should not read .env by default.
Operators who use fixed CONSOLE_TOKEN must expose it as process env or rely on
.proxy-gateway/console-token.
```

The script should not read production `.env` or any other secret source. This
keeps token handling explicit and avoids expanding a local diagnostic helper
into a broader secret resolver before there is a proven operational need.

## Revisit Conditions

Revisit `.env` token lookup only if at least one of these becomes true:

- `network-doctor.ps1 repair` frequently fails because `.env` `CONSOLE_TOKEN`
  is not loaded into the PowerShell process;
- the local token store is unavailable, intentionally disabled, or no longer
  considered a supported source;
- operator workflows require fixed `.env` tokens without separate process-env
  setup;
- tests can cover process env, token store, `.env` fallback, precedence,
  malformed `.env`, missing files, and non-disclosure of token values;
- implementation can guarantee it reads only the intended local project `.env`
  and never production secret material.

## Follow-Up If Approved

If this spec is accepted, the next implementation PR should remain docs-only:

1. Update `README.md` to clarify `network-doctor.ps1` token lookup sources.
2. Update `docs/NETWORK_FORWARDING.md` with the same boundary.
3. Do not change `scripts/network-doctor.ps1`.
4. Do not change `scripts/proxy.ps1`.
5. Validate with `git diff --check`.

## Acceptance Criteria

- The spec clearly states the current token lookup sources.
- The spec clearly states that `.env` is not read by default.
- The recommendation is Option A+.
- Future conditions for revisiting `.env` lookup are explicit.
- No PowerShell implementation changes are included.
- No runtime, AWS, production, Nginx, systemd, backend auth, Admin UI, or deploy
  changes are included.
- No real secrets, tokens, generated subscription URLs, or customer data are
  added.
