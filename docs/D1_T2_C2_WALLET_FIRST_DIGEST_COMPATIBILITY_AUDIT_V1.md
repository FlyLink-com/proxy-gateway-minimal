# D1 T2-C2 Wallet-first Handoff Digest Compatibility Audit v1

> **Status:** SOURCE AUDIT COMPLETE; COMPATIBILITY RECOMMENDATION FOR OWNER REVIEW. No production values were read and no source behavior was changed by this document.
> **Source anchor:** `feat/c1-risk-a-proof-window-contract-20261108@96c2b455b215b8eda01b6a562cdcaeaf942e7aaa`.
> **Related ADR:** `docs/D1_T2_C2_KEY_CUSTODY_AND_ROTATION_ADR_V1.md`.
> **Production authority:** BWH remains the only production writer.

## 1. Finding

The Wallet-first setup-delivery handoff uses two purpose-separated SHA-256 digests:

- `idempotency_key_hash`
- `session_binding_hash`

They are not email/IP/account PII pseudonyms and are not members of the six raw idempotency domains covered by the C2 HMAC primitive. The current implementation hashes the raw transient input in memory and persists only a 64-character lowercase hexadecimal digest.

The source uses distinct domain labels:

```text
SHA-256(UTF8("GCCWEBOS:WALLET_FIRST_SETUP_DELIVERY_IDEMPOTENCY:v1\0") || UTF8(idempotencyKey))
SHA-256(UTF8("GCCWEBOS:WALLET_FIRST_SETUP_DELIVERY_SESSION:v1\0") || UTF8(sessionRef))
```

The NUL byte is a real domain separator. Do not change the byte sequence or label during compatibility-preserving migration.

## 2. Source evidence

### 2.1 Digest creation

`server/services/platform/wallet-first-current-resource-setup-delivery.mjs`:

- `hashValue(domain, value)` computes SHA-256 over `domain + NUL + value`.
- `deliverSetup()` uses the two distinct labels above.
- Only the resulting hashes are passed to the control store.
- The raw idempotency key and session reference are not returned to the store.

### 2.2 Session binding source

`server/services/platform/user-portal-auth.mjs`:

- The default Portal session reference factory uses `randomBytes(12).toString("hex")` (96 bits of random input).
- The Portal setup route obtains the session through `requirePortalHeaderSession()` and passes `session.sessionRef` to the delivery service; the request body contains only `idempotencyKey`.
- Browser sessions are based on a 32-byte random cookie value and are represented internally by a derived session identifier.

The digest is therefore bound to the authenticated server-side session reference, not a session value supplied in the JSON request body.

### 2.3 Idempotency-key source and one source gap

`admin/src/features/user-portal/user-portal-page.tsx`:

- `nextPortalSetupIdempotencyKey()` uses `crypto.randomUUID()` when available.
- Its current fallback uses `Date.now()` and `Math.random()`. This fallback does not provide a cryptographically secure entropy guarantee and must be removed.
- The server-side Wallet-first validator currently accepts a broader 16–128 character grammar rather than enforcing the canonical UUID generated by the first-party UI.

Recommended hardening is to use `crypto.getRandomValues()` to construct a UUIDv4 when `randomUUID()` is unavailable (or fail closed if secure randomness is unavailable), and to enforce the same canonical UUIDv4 contract at the Wallet-first service boundary. Keep the legacy non-Wallet-first setup path unchanged unless its own callers are separately audited.

### 2.4 Persisted state and replay behavior

`server/services/platform/wallet-first-setup-delivery-handoffs-migrations.mjs` defines:

- Both digest columns as nullable 64-character lowercase hexadecimal strings.
- `pending` rows have neither digest.
- `claimed` and `delivered` rows require both digests.
- `reconciliation_required` rows clear both digests.
- A claim lease is passed by the delivery service as 600,000 ms (10 minutes).
- The handoff state machine also binds claim generation, account, resource, and session compare-and-set behavior.

`server/tests/wallet-first-setup-delivery-handoffs.test.mjs` proves that the raw synthetic idempotency/session values are not persisted and that replay with the same digest is stable while a different session binding loses the claim.

The 10-minute lease is a claim/reclaim window, not evidence that the persisted row is deleted after 10 minutes. The inspected schema and delivery service do not establish a terminal-row purge period. Do not infer retention from the lease.

## 3. Recommended compatibility decision

**Retain the existing domain-separated SHA-256 v1 digests for this specific Wallet-first handoff contract; do not convert them to HMAC merely for algorithm uniformity.**

Conditions:

1. Remove the `Math.random()` fallback and use only cryptographically secure UUID generation.
2. Enforce canonical UUIDv4 idempotency keys at the Wallet-first service boundary, matching the first-party UI.
3. Continue to derive `session_binding_hash` only from an active authenticated Portal session reference; never accept it from a request body or client-supplied digest.
4. Preserve both exact v1 domain strings and NUL-byte encoding for all existing and in-flight rows.
5. Keep the D1 target fields as 64-character lowercase hex under an explicitly named `sha256-domain-v1` contract. Do not label these values as HMAC or PII pseudonyms.
6. Do not attempt to re-key existing digests. SHA-256 outputs cannot be converted to HMAC without the original raw input, which is deliberately not persisted.
7. Do not add these values to the PII HMAC key family. Their purpose, entropy source, and replay lifecycle are distinct.

This avoids a needless key-custody dependency and preserves the existing idempotency/session-CAS behavior. If a later security review requires HMAC, it must be a new versioned contract with a dual-read window and explicit treatment of in-flight rows; never reinterpret existing 64-hex values as HMAC.

## 4. Retention decision still required

The current source establishes the 10-minute claim lease but does not establish when delivered handoff rows or their two digests are purged.

Recommended rule to evaluate:

- Pending/claimed rows remain governed by the existing 10-minute lease and claim-generation state machine.
- A delivered row must retain enough state to preserve the approved idempotent acknowledgement/replay behavior.
- Purge only after the owner-approved replay/acknowledgement window has elapsed and the external escrow has been verified as acknowledged/tombstoned.
- A failed or ambiguous escrow cleanup remains `reconciliation_required`; it must not be purged as if deletion succeeded.
- The exact post-delivery retention duration must be selected from the actual product retry/support requirement. The source does not justify inventing a numeric TTL.

This is one bounded owner decision, not a reason to block unrelated C1/C3/C4/C5 synthetic work.

## 5. Required synthetic acceptance tests

1. First-party UUIDv4 generation uses `randomUUID()` when available.
2. The fallback uses `getRandomValues()` and produces valid UUIDv4 version/variant bits.
3. If secure randomness is unavailable, generation fails closed; `Math.random()` is never used.
4. Wallet-first service rejects malformed, low-entropy, and non-canonical idempotency keys.
5. Session binding is derived only from the authenticated active session supplied by the Portal route.
6. The two exact domain labels remain distinct and include the NUL separator.
7. Existing v1 replay and same-session acknowledgement remain stable.
8. The D1 target schema preserves the 64-lowercase-hex v1 contract and does not misclassify these columns as PII HMAC fields.
9. Retention/purge tests cover delivered, expired-claim, reconciliation-required, and escrow-tombstone states after the owner-selected window.
